@AGENTS.md

## What this is

A restaurant ordering site (Next.js App Router + Postgres). Customers browse the menu, order, and track live status; the restaurant owner manages menu/stock/orders from `/admin`. Payment is currently simulated — no real payment gateway is wired up.

## Commands

```bash
npm run dev          # start dev server (Turbopack)
npm run build         # production build — also runs TypeScript checks
npm run lint           # eslint

npm run db:studio     # Prisma Studio GUI against the real Neon database
npm run db:seed       # (re)seed categories, menu items, owner + test customer accounts
npm run db:migrate    # prisma migrate deploy (non-interactive, used in production/CI)
```

There is no test suite in this project yet.

### Migrations must be created by hand in this environment

`prisma migrate dev` requires an interactive TTY and will fail in non-interactive shells (including Claude Code's Bash tool) with `Prisma Migrate has detected that the environment is non-interactive`. `prisma migrate diff` against a migrations directory also fails here because no shadow database is configured.

Workflow for schema changes:
1. Edit `prisma/schema.prisma`.
2. Manually create `prisma/migrations/<timestamp>_<name>/migration.sql` with the raw SQL for the change.
3. Apply it with `npx prisma migrate deploy` (non-interactive, safe in this environment).
4. Run `npx prisma generate` to regenerate the client.

## Architecture

### Database access — Prisma 7 + Neon serverless driver adapter

Prisma 7 dropped the `datasource.url` field from `schema.prisma` — the connection string lives only in `prisma.config.ts` (CLI/migrations) and is passed explicitly to `PrismaClient` at runtime via a driver adapter. There is no plain `DATABASE_URL`-only setup here.

- `src/lib/db.ts` — the shared `prisma` client singleton. Constructs a `PrismaNeon` adapter from `@prisma/adapter-neon`, and sets `neonConfig.webSocketConstructor = ws` because the Neon serverless driver needs a WebSocket implementation in the Node.js runtime (this is required — omitting it throws `fetch failed` at query time).
- The generated client lives at `src/generated/prisma/` (gitignored, regenerated by `prisma generate`, wired via `postinstall`). **Import from `@/generated/prisma/client`, not `@/generated/prisma`** — there is no index file at the package root, only `client.ts` (the documented entry point) alongside per-model files.
- `prisma/seed.ts` constructs its own adapter/client rather than importing `src/lib/db.ts`, since it runs standalone via `tsx` outside the Next.js process.

### Auth — Auth.js v5, JWT sessions, single `User` table with a `role` column

`src/auth.ts` is the NextAuth config (Credentials provider only, bcrypt password comparison against `User.passwordHash`). There is no separate admin/customer table — `User.role` is `"CUSTOMER" | "OWNER"`, and that's what distinguishes an owner from a customer. Session type augmentation (`id`, `role` on the session user) is in `src/types/next-auth.d.ts`.

`/admin/*` routes are gated by `src/proxy.ts` (Next 16's renamed `middleware.ts` convention — the file **must** be named `proxy.ts`, and it runs on the Node.js runtime by default, so it can safely import `auth()` → Prisma → the Neon `ws` adapter without edge-runtime incompatibilities; do not add `export const runtime = "nodejs"` here, Next 16 rejects that as redundant on `proxy.ts`). Every admin **server action** additionally calls `requireOwner()` (`src/lib/auth-helpers.ts`) as defense in depth, since a server action can in principle be invoked directly without going through the page/proxy check.

Because `Header` (`src/components/Header.tsx`) is an async Server Component that reads the session via `auth()`, it **cannot be imported into a Client Component** (Next.js will fail the build). Pages needing client-side interactivity (cart, checkout, forms) are split into a server `page.tsx` that renders `<Header />` plus a separate `"use client"` subcomponent for the interactive part — see `src/app/cart/page.tsx` + `CartView.tsx`, or `src/app/checkout/page.tsx` + `CheckoutForm.tsx` for the pattern to follow.

### Cart — client-only, not persisted server-side until checkout

`src/lib/cart-context.tsx` is a React Context + `useReducer`, persisted to `localStorage`, wrapping the whole app from `src/app/layout.tsx`. Nothing about the cart touches the database until `placeOrder` (`src/app/checkout/actions.ts`) runs.

### Order placement — server action, transactional, concurrency-safe stock decrement

`placeOrder` in `src/app/checkout/actions.ts` re-derives prices from the database (never trusts client-sent prices) and decrements `MenuItem.stockQty` via `updateMany({ where: { stockQty: { gte: quantity } } })` rather than a plain `update`, so two simultaneous checkouts for the last unit of an item can't both succeed — the loser's `updateMany` matches zero rows and the whole transaction throws. Guest checkout is supported (`Order.userId` is nullable); if a session exists, the order is linked to that user.

### Static pages + revalidation

`/` and `/menu` are statically prerendered by default (they read the DB at build/request time with no `dynamic` export). Any mutation that changes what they'd show — `placeOrder` (stock decrements) and every mutation in `src/app/admin/actions.ts` (menu CRUD, stock, availability) — calls `revalidatePath("/")` / `revalidatePath("/menu")` afterward. If you add a new mutation that changes menu or stock data, remember the revalidation call or the storefront will silently serve stale data until the next deploy.

### Live order status — polling, not websockets

`src/components/OrderStatusTracker.tsx` (client component) polls `GET /api/orders/[id]` every 4s while the order is in a non-terminal state, and stops once it hits `DELIVERED`/`CANCELLED`. This was a deliberate choice over Postgres LISTEN/NOTIFY or a push service — see the project's architecture discussion for tradeoffs. If a "true push" upgrade is ever wanted, this is the component/endpoint to replace.

### Menu item photos — emoji + fixed Tailwind gradient palette, no image uploads

There's no image storage yet; dishes are rendered as an emoji over a Tailwind gradient (`src/components/DishPhoto.tsx`). The gradient class strings **must** come from `src/lib/gradients.ts` (`DISH_GRADIENTS`) rather than arbitrary free text — Tailwind's build-time class scanner only generates CSS for class names it can find as literal strings in the source tree, so an admin-entered arbitrary gradient string would silently produce no styling. The admin menu form (`MenuItemForm.tsx`) enforces this via a `<select>` bound to that constant; don't change it to a free-text input without also handling the Tailwind safelist implication.

### Order status flow

Canonical status list/labels/colors live in `src/lib/order-status.ts` (`ORDER_STATUS_FLOW`, `ORDER_STATUS_LABEL`, `ORDER_STATUS_COLOR`) and are shared by the customer tracker, the admin order list, and the order confirmation page — update there, not per-component, if statuses change.

## Environment variables

- `DATABASE_URL` — Neon Postgres connection string (pooled).
- `AUTH_SECRET` — Auth.js session secret.

Both live in a gitignored `.env` (not `.env.local` — `prisma.config.ts` and the app both read `.env`; consolidate here rather than reintroducing `.env.local`). The same values must also be set in Vercel's project environment variables for the deployed site.

## Seeded accounts

`npm run db:seed` creates:
- Owner: `owner@foodie.test` / `owner123`
- Test customer: `customer@foodie.test` / `customer123`

There is no self-service way to create additional owner accounts (by design — public signup always creates `CUSTOMER` role). Promoting a user to `OWNER` currently requires a direct database edit (Prisma Studio or a one-off script).
